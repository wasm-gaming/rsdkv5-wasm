# Engine app: boot screen and pause menu (Sonic Mania)

2026-11-13 15:36 · follows rsdkv4-wasm `RECORD/2026-11-13.engine-app-load-game-and-pause.WIP.md`
(owner: "la 2, apps para rsdkv3 y rsdkv5"). **Status: proposed, awaiting approval.**

## Goal
rsdkv5-wasm ships its own `EngineApp` (engine-specs 0.4.0 contract, `UX.md`) so a host mounts
`<engines>/rsdkv5/app/app.js` and gets the same screens and gamepad behaviour as rsdkv4.

## What is different from rsdkv4 (why this is not a copy)
rsdkv4's load-game screen is built on a native bridge that rsdkv4 injects in `scripts/build.sh`
(`SkipStartMenu`, `web_get_save_slots`, `web_start_game`, `web_get_players`): RSDKv4's
start menu is native C++ code, so the app can replace it. Here there is no such bridge:
Sonic Mania's menus are game code (`UISaveSlot`, `MenuSetup`). `SaveData.bin` is readable
from JS (`SaveRAM`: characterID, zoneID, lives, score, collectedEmeralds…, one 0x400-byte block per
slot, encore slots after), but *starting* a slot means calling into the game's own save logic.
So the craft-style slot screen can't be copied over; it would need new native code. This record
covers what can ship now without touching the wasm; the slot screen is listed as a later phase.

## Phase A — this record (no wasm rebuild)
- **Where:** `src/app/app.js` + `src/app/app.css` → `dist/rsdkv5/app/` (Makefile `build-app`, part
  of `build-sdk`); `package.json` exports `./app` and ships `src/app/`. Plain JS + DOM, imports
  only `../rsdkv5.sdk.js`; styles read engine-specs `--wg-*` tokens with fallbacks. Same structure,
  state machine, pointer handling and confirm dialog as rsdkv4's app (copied, not shared:
  engines stay independent).
- **`mount(target, host)`:** boot screen (game art + "Arrancando…") while the SDK starts with
  `host.assets` / `host.storage`; then straight into the game, which shows **its own** title and
  save select. Input suspended in game.
- **Pause** (Select+Start / Escape / F1): engine paused with owner `app`. Items: *Continuar*;
  the game's own screens found by name in the live stage list (`devMenu.getStageList()`, e.g.
  title screen / save or main menu / level select) — shown only if present, loaded with
  `devMenu.loadStage()`; *Volver al lanzador* (asks first). B / Start closes.
- **Error screen**, **unmount** (listener off, SDK destroyed, DOM removed) as in rsdkv4.
- **Tests:** a node test for the pure parts (pause-item lookup from a fake stage list).
- **Verification:** Chromium with the published wasm and a stub host; with no Data.rsdk here,
  the boot/error path and the menus are checked with a fake SDK. Real-game check is the owner's.
- **Version:** left to the release workflow (minor).

## Phase B — later, needs approval of its own
Craft-style load-game screen: parse `SaveData.bin` in JS for the cards (zone, character, emeralds, lives, score); start a slot
through new glue in `scripts/build.sh` that runs Mania's own `SaveGame`/`MenuSetup` path for that
slot (and skips the title) — a wasm rebuild, and a real Data.rsdk to verify.

## Out of scope
Options screen; the launcher's `engines.json` (play.germade, not in this session).

`getStageList()` returns `[]` and the app can't offer the game's screens. Plan:

- `scripts/build.sh` writes `RSDKv5/RSDK/Dev/WebDevMenu.cpp` (embind) into the checkout:
  - `web_devmenu_get_stage_list()` → JSON `[{ name, stages: [{ name }] }]` from
    `sceneInfo.listCategory[0..categoryCount)` / `sceneInfo.listData[sceneOffsetStart..End]` — the
    same shape rsdkv3/rsdkv4 return, so the app and SDK need no change;
  - `web_devmenu_load_stage(category, index)` → what the engine's own dev menu does:

    (bounds-checked; ignored otherwise);
  - `web_devmenu_set_paused(bool)` stays absent: the SDK's `pauseMainLoop()` already freezes the game.
- The file is added to the engine's CMake sources and the link gets `--bind`; each insertion
  asserts it applied.
- Build here with Docker (emscripten ports seeded from git: GitHub archives are blocked by this
  environment's proxy, git and release downloads are not — local workaround only, nothing in the
  repo changes for it).
- Verify: the built wasm exports the three names; in Chromium with dummy data the bridge returns

## Extension · 2026-11-13 20:10 — Point 3 (phase B): plan, awaiting approval

Owner: "dale a los 4 puntos". What it takes, found reading Sonic-Mania-Decompilation @ `9dc69942`:

- **Cards (JS only):** parse `SaveData.bin` (the SDK already mirrors it): `SaveRAM` blocks of
  0x400 bytes (int32, little-endian), slots 0-7 regular, 8+ Encore; `saveState`, `characterID`,
  `zoneID`, `lives`, `score`, `collectedEmeralds` (bit mask), `continues`. Mania has its own
  portraits: the app would show zone names (Green Hill … Titanic Monarch, Egg Reverie) without art.
- **Starting a slot (native, in the game, not the engine):** Mania does it in
  `MenuSetup_SaveSlot_ActionCB`: sets `globals->saveSlotID/gameMode/medalMods/playerID`, for a new
  slot rewrites the block (`saveState = 1`, `characterID`, `lives = 3`…), saves the file, then
  `RSDK.SetScene("Mania Mode", "")` + `TimeAttackData_GetManiaListPos(zone, ACT_1, character)`, or
  the Angel Island cutscene for a new game. A `web_mania_start_slot(slot, character)` compiled into
  the game library would replay that without the menu; it needs the save file already loaded
  (`globals->saveLoaded`), so it can only run once the title screen is up.
- **Risk:** it writes the player's save file. Without Mania's `Data.rsdk` here, nothing of it can
  be checked; a wrong offset or state would corrupt real saves.

Proposal: implement only after the owner can test with a real pack, behind an explicit
`startMenu: 'host'` config (default stays Mania's own menus), and read-only cards first.

## Extension · 2026-11-13 20:45 — Phase B (Mania load-game screen): approved; detailed plan

Owner: "sí, sigue con la fase B de Mania" (now testable here with the owner's real data).
Found in Sonic-Mania-Decompilation @ `9dc69942` (the build's pin; the data is Plus, VER_106):

- **File:** `SaveData.bin` = `globals->saveRAM` (`int32[0x4000]`, 64 KiB). Regular slot `s` (0-7)
  is the 0x400-byte block at `0x400 * s`; Encore slots at `0x400 * (s % 3 + 10)`. `SaveRAM` fields
  (little-endian int32) from +0x58: `saveState` (0 blank, 1 in progress, 2 complete), `characterID`
  (0 Sonic & Tails, 1 Sonic, 2 Tails, 3 Knuckles, 4 Mighty, 5 Ray), `zoneID`, `lives`, `score`,
  `score1UP`, `collectedEmeralds` (bit mask, 7 bits), `continues`, …
- **Starting a slot (Plus):** `UISubHeading_SaveButton_ActionCB` (not `MenuSetup_…`, pre-Plus):
  `gameMode = MODE_MANIA`, `saveSlotID`, `medalMods = 0`; a new slot is cleared and seeded
  (`saveState 1`, `characterID`, `zoneID 0`, `lives 3`); `playerID` from the character (+ Tails
  assist for 0); then `SetScene("Cutscenes", "Angel Island Zone")` for a new game, or
  `SetScene("Mania Mode", "")` + `TimeAttackData_GetManiaListPos(zone, ACT_1, character)`; the save
  file is written and the scene loads in its callback. The save must be loaded first
  (`SaveGame_LoadFile`, `globals->saveLoaded == STATUS_OK`); Plus only loads it in the menus.

**Changes**
1. Native, in the **game** library (the logic and `globals` live there): `scripts/build.sh`
   appends to `SonicMania/Objects/Menu/UISubHeading.c` (asserted):
   - `web_mania_save_status()` → loads the save if needed (`SaveGame_LoadFile`), returns
     `globals->saveLoaded`;
   - `web_mania_start_slot(slot, character)` → the steps above for Mania Mode (no Encore, no
     secrets / medal mods, no menu-tag bookkeeping, no spinner), callback = `RSDK.LoadScene()`;
     returns 0 if the save isn't loaded or the slot is out of range.
   Exported (`EMSCRIPTEN_KEEPALIVE` + `EXPORTED_FUNCTIONS`).
2. SDK: `play.saves` — `list()` parses `SaveData.bin` from the working dir (8 slots: state,
   character, zone, zone name, lives, score, emerald count); `ready()` polls the native status;
   `start(slot, character)`; slots are written by Mania itself (the SDK only reads).
3. App: a load-game screen before the game, rsdkv4's craft cards adapted to Mania (8 slots +
   NO SAVE → Mania's own menus; zone name + character instead of portraits; emeralds; lives,
   score; character picker on an empty slot, Mighty/Ray only if the data has them). The game
   boots behind it paused; a slot starts it. Pause gains *Cambiar de partida*. If the native
   side is missing (older wasm) or the save can't be loaded, the app falls back to phase A.
4. Tests: `SaveData.bin` parser with a synthetic file; Chromium with the real data: new game in
   an empty slot (Angel Island intro), save written, reload → the slot shows it, continue it.

**Risk handling:** the app never writes `SaveData.bin` itself; Mania does, through its own
`SaveGame_SaveFile`. Tests run against a scratch OPFS namespace, never the owner's.

## Extension · 2026-11-14 — The dialog over the cards, and its backdrop

Owner (screenshot of rsdkv4's "¿Volver al lanzador?" in the launcher): "esta maquetación está mal" —
the character art on the slot cards showed **over** the dialog — and "y podría tener algún fondo".

- Cause: the cards' art is `position: relative; z-index: 1`; the dialog layer was positioned with no
  `z-index`, so the art painted over it; the panel was translucent over a light dim.
- Fix (the same in the five apps — rsdkv4, rsdkv5, rsdkv3, blastem, fbneo — which share this CSS):
  the dialog layer gets `z-index: 10` and a real backdrop (darker, blurred); the panel in it is opaque
  with a tint of the game's accent; `.slot-cards` gets `isolation: isolate` so the art's z-index stays
  in the row; the dialog title fits one line in the launcher's display face (Unbounded), and the
  panel is a bit wider.
- Verified (Chromium, with the launcher's fonts): rsdkv4 with the real `Sonic1.rsdk` and rsdkv5 with
  the real `SonicMania.rsdk`, exit confirm over the slot screen: the dialog above everything, the
  slot screen blurred behind it, the title on one line.
- Release: **patch**.

Commit: `fix(app): dialogs above the cards, on a backdrop of their own`
